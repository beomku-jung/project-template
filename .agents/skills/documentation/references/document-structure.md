# 문서 구조·Markdown·출처

실행 순서·명령 선택·API 설명의 중복·Markdown 링크를 정리할 때 읽습니다.
표준 적용·적합성 판단, 제품 사용 설명서 작성·검토, ASD-STE100 검토를 요청받으면 [출처와 적용 범위](#출처와-적용-범위)를 읽습니다.

## 구조는 정보의 관계에 따라 선택하기

### 따라 할 순서가 있으면 번호 목록

아래 명령이 정의된 프로젝트의 절차 예제입니다. 설치·자동 수정은 파일을 바꿀 수 있습니다.

**짧은 안내**

> `pnpm install`로 설치하고 `pnpm fix`로 수정한 뒤 `pnpm check`로 검사합니다.

**단계별로 따라 할 때**

```markdown
저장소 루트에서 실행합니다.

1. `pnpm install`로 의존성을 설치합니다.
2. `pnpm fix`로 린트·포맷을 자동 수정합니다.
3. `pnpm check`로 검사합니다.
```

### 목적별로 고르면 표

아래는 실행 위치·필수 설정 등 비교 조건이 늘어날 때 확장해 쓸 표의 기본 형식입니다.

```markdown
| 목적                     | 명령         |
| ------------------------ | ------------ |
| 린트·포맷 자동 수정      | `pnpm fix`   |
| 파일 수정 없이 전체 검사 | `pnpm check` |
```

자동 수정과 파일 수정 없는 검사만 고르면 “수정하려면 `pnpm fix`를, 파일 수정 없이 검사하려면 `pnpm check`를 실행합니다”처럼 한 문장으로 쓸 수 있습니다. 실행 위치·필수 설정 등 추가 실행 조건도 비교해야 하면 표로 나눕니다.
설치·검사·문제 해결처럼 독립된 주제는 같은 위계의 제목으로 나눕니다.

## 중복을 줄여도 사용 조건은 남기기

제목·타입·예제에서 이미 알 수 있는 정보는 덜어냅니다.

```ts
export * from "./parse-input.ts";
export type * from "./transport.ts";
```

모듈 구현을 생략한 재수출 예제입니다. `export *`와 `export type *`의 차이를 옆 설명에서 반복하지 않습니다.
코드에 없는 지원 환경·오류·부수 효과는 남깁니다. 예를 들어 `check`가 첫 실패에서 중단한다면 실행 위치·성공 기준과 함께 `첫 실패 이후의 검사는 실행되지 않습니다`를 설명합니다.

### API 수명 설명으로 내용 범위 정리하기

요청: **제공된 근거로 API 수명 설명을 보완하고, 운영 검토 항목은 별도 운영 지침으로 이동**. 표현만 다듬는 작업이 아닙니다.
예제에서는 쓰기 완료를 기다리고 직접 연 파일만 종료하며 주입받은 파일은 호출자가 종료한다는 근거가 제공됐다고 가정합니다.

- 원문: 직접 연 파일을 닫습니다. 풀의 재사용·서비스 재시작·싱글턴의 테스트 격리도 검토합니다.
- API 수명 절: 쓰기 완료를 기다린 뒤 직접 연 파일을 닫습니다. 주입받은 파일의 종료 책임은 호출자에게 남습니다.
- 운영 지침으로 옮겨 유지할 항목: 풀의 재사용·서비스 재시작·싱글턴의 테스트 격리 검토.

API 절에는 근거로 확인한 완료 시점·소유권을 적고, 운영 검토 의무는 요청된 위치로 옮깁니다. 표현 수정만 요청받았다면 항목을 이동·삭제하거나 계약을 추가하지 않습니다.

## Markdown 외부 링크

자료 하나는 설명 가까이에 두고, 링크 이름에 확인할 내용을 씁니다.

```markdown
참고: [pnpm 패키지 선택](https://pnpm.io/filtering)

대상 패키지는 [pnpm 필터](https://pnpm.io/filtering)로 선택합니다.
```

문맥에 맞는 방식 하나를 고릅니다. 여러 자료는 참고 목록으로, 다른 주제는 소제목으로 묶습니다. 항목마다 `참고:`를 반복하지 않습니다.

```markdown
## 참고

### 실행 명령

- [pnpm 패키지 선택](https://pnpm.io/filtering)
- [Vitest 프로젝트별 실행](https://vitest.dev/guide/projects.html#running-tests)

### 문서 구성

- [GitHub README 안내](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)
```

## 출처와 적용 범위

예제는 자체 작성했으며 외부 지침의 예문·표를 옮기지 않았습니다.

### 독자 중심 기술 문서

- [ISO 24495-1:2023 공개 개요](https://www.iso.org/standard/78907.html): 언어에 한정되지 않는 쉬운 언어 원칙으로 기술 문서에도 적용할 수 있습니다. 유료 전문은 확인하지 않았습니다.
- [국제 쉬운 언어 연맹의 공개 해설](https://www.iplfederation.org/wp-content/uploads/2024/06/Plain-language-certification-for-organizations_A-Consultation-Paper-1-1.pdf): 관련성·검색 용이성·이해 가능성·사용 가능성을 참고합니다. 이 스킬로 표준 적합성·조직 인증·실제 독자의 성공을 판정하지 않습니다.

### 별도 검토 요청의 출처

제품 사용 설명서 검토를 요청받으면 [KS C IEC/IEEE 82079-1 공개 목록](https://www.kssn.net/search/stddetail.do?itemNo=K001010145434)에서 제품 사용 정보의 작성·구성 범위를 확인합니다.
목록·범위만 참고했으며, 전문 없이 조항별 적합성을 주장하지 않습니다.
한국어 어휘·문법이나 모든 README의 작성 규칙으로 쓰지 않습니다.

영어 통제 언어 검토를 요청받으면 [ASD-STE100 소개](https://www.asd-ste100.org/about_STE.html)와 [공식 Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf)를 참고하고, 요청한 판본의 전체 규칙·사전으로 검토합니다.
영어용이므로 한국어에 단어 수·사전 제한을 적용하지 않습니다.
[배포·사용 조건](https://www.asd-ste100.org/STE_downloads.html)을 확인하고 원문 규칙·사전을 복제하지 않습니다.
