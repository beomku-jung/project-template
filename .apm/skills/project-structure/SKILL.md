# 도메인 중심 구조 설계

새 책임은 업무 규칙·상태를 소유한 기존 도메인에 둡니다. 요구사항·실제 업무 흐름·용어와 기존 코드를 대조해 소유자를 정합니다.

## 책임 배치 예제

```text
orders/
├── checkout/       # 주문 확정 조건·금액 계산
└── cancellation/   # 취소 조건·주문 상태 변경·환불과 배송 중단 요청
payments/           # 결제 승인·환불 조건과 결제 상태
shipping/           # 출고 조건과 배송 상태
```

주문 취소 흐름은 결제·배송 도메인이 제공하는 판단·처리 결과를 이용합니다.
각 도메인의 상태 변경은 해당 도메인이 수행합니다.

## 작업별 기준

### 경계와 공통화

기존 도메인과 업무 의미·상태 전이·불변 조건·변경 이유가 다르면 별도 경계를 정합니다. 파일 수·자료형·이름의 유사성만으로 합치거나 분리하지 않습니다.

- 여러 흐름이 같은 업무 규칙을 쓰면 소유 도메인의 공개 계약을 재사용합니다. 호출자가 많아졌다는 이유로 규칙을 `shared`·`common`으로 옮기지 않습니다.
- 업무 규칙·특정 도메인의 상태에 의존하지 않고 모든 사용처에서 의미·실패 조건·변경 이유가 같은 코드만 공통 영역에 둡니다. 아직 그 관계가 확인되지 않으면 각 소유자 안에 둡니다.
- 새 계층은 맡을 입력·결과·책임과 기존 책임에서 분리되는 이유를 설명할 수 있을 때 추가합니다. 폴더 모양을 맞추기 위한 전달 계층은 추가하지 않습니다.

공통화 전후의 사용처에서 같은 입력·실패가 같은 업무 의미를 갖는지 대조합니다. 서로 다른 정책을 옵션으로 숨겨 공통화하지 않습니다.

### 의존 방향과 연동

| 책임                          | 담당 영역                         |
| ----------------------------- | --------------------------------- |
| 업무 계산·검증·상태 전이      | 해당 도메인                       |
| 여러 도메인을 잇는 업무 흐름  | 그 흐름을 맡은 도메인의 조정 역할 |
| 저장·외부 서비스의 자료 변환  | 도메인과 외부 시스템의 연결 경계  |
| 화면 문구·응답 형식·전달 방식 | 각 소비자 경계                    |

도메인 간 요청은 소유자가 제공하는 공개 계약으로 연결합니다. 입력·결과·실패의 업무적 의미와 상태 변경 책임을 정하고, 호출자가 소유자의 내부 저장소·테이블·상태 필드를 직접 수정하지 않게 합니다.
업무 계산·상태 전이는 저장소·HTTP·화면 형식 없이 표현하고, 외부 시스템의 자료 구조·상태값은 연결 경계에서 도메인의 용어로 변환합니다.
순환 의존성이 생기면 조정 역할이 필요한 호출 순서를 소유하고, 각 도메인은 자신의 판단·상태 전이만 제공하도록 나눕니다. 순환을 끊으려고 업무 규칙을 무소유 공통 영역으로 옮기지 않습니다.

### 기존 경계 변경

아래 데이터 보존·초기화 조건을 충족하고 모든 소비자를 함께 옮길 수 있으면 한 번에 전환하고 옛 호출·별칭·중복 구현을 제거합니다. 사용자 데이터나 동시 전환할 수 없는 소비자가 확인된 경우에만 변환·호환 경로를 둡니다.

| 확인한 근거                                                                                                                         | 처리                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 호출부·진입점·배포 대상을 확인해 모든 소비자를 함께 바꿀 수 있고, 저장 데이터가 없거나 재생성 원본·절차와 초기화 허용 범위가 확인됨 | 모든 호출부를 새 계약으로 이전하고 옛 경로 제거; 영향·재생성 또는 초기화 방법 안내            |
| 스키마·저장소·운영 기록에서 보존할 사용자 데이터가 확인됨                                                                           | 기존 데이터의 새 계약 변환, 변환 전 보관·실패 시 복구 절차를 정하고 보존 항목을 대조          |
| 외부 공개 API·배포 버전·소비자 목록에서 동시 전환이 불가능한 소비자가 확인됨                                                        | 지원할 계약·소비자와 호환 종료 조건을 명시하고 전환 기간의 호출 경로 제공                     |
| 소비자 범위·데이터 소유자·재생성 또는 복구 가능성이 불명확                                                                          | 관련 선언·호출부·스키마·운영 자료를 읽기 전용으로 확인하고 삭제·초기화 보류; 미확인 항목 명시 |

검색에서 호출부가 안 보인다는 이유만으로 외부 소비자나 운영 데이터가 없다고 단정하지 않습니다.
변환·호환 경로에는 지원 대상과 제거 조건을 정합니다. 전환 후 새 계약의 정상·실패 흐름과 보존할 데이터를 이전 계약과 대조하고, 호환 대상이 남아 있으면 해당 경로도 확인합니다.

## 결과 확인

- 대표 업무 흐름의 각 계산·판단·상태 전이에 소유자가 하나 있고, 호출이 소유자의 공개 계약을 거치는지 추적합니다.
- 같은 규칙의 중복 구현과 다른 도메인의 내부 상태 직접 수정이 없어야 합니다. 공통 코드가 특정 도메인의 규칙·상태를 참조하지 않는지 확인합니다.
- 분리·공통화의 근거, 확인한 소비자·데이터 자료, 유지할 호환 대상 또는 옛 경로 제거 범위를 남깁니다.
- 설계안에는 정상·실패 흐름과 데이터 보존·복구의 비교 대상·성공 조건을 적습니다. 구조 변경을 수행했다면 해당 흐름·데이터로 실제 확인한 결과를 구분해 보고합니다.
- 확인하지 못한 소비자·운영 데이터·복구 조건과 실행하지 않은 검증을 밝힙니다.
