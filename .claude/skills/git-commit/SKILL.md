# Git 커밋

커밋 생성·기존 커밋 재작성·푸시는 각각 해당 작업을 명시적으로 요청받은 경우에만 수행합니다.

- 메시지 작성·수정 요청에 대상 기존 커밋의 재작성 요청이 없으면 초안만 제공하며 파일·인덱스를 바꾸지 않습니다.
- 커밋 생성 요청: 요청 범위로 새 커밋을 만듭니다.
- 대상 기존 커밋과 재작성을 함께 요청하면 해당 커밋의 메시지·내용 중 요청한 부분을 재작성합니다. “마지막 커밋 메시지 고쳐줘”가 여기에 해당합니다.
- 푸시 요청: 원격 반영을 수행합니다. 이력 재작성이나 일반 푸시 요청을 강제 푸시 권한으로 넓히지 않습니다.

변경 범위와 메시지의 근거로 작업 트리·인덱스·기존 커밋·저장소 규칙을 읽습니다.

## 메시지 작성

제공된 변경 내용이나 요청 대상 diff를 근거로 한글 개조식으로 요약합니다. “스테이징한 변경”의 메시지는 인덱스만, 특정 커밋의 메시지는 해당 커밋만 대상으로 하며 다른 변경을 섞지 않습니다.
아래 한글 Conventional Commit 형식을 기본으로 하고, 저장소에 다른 형식·길이 규칙이 명시돼 있으면 그 규칙을 적용합니다. commitlint 설정이 있으면 초안도 실제로 검사하고, 실행한 검사의 결과만 보고합니다. 검사를 실행하지 못했다면 이유를 밝히고 통과했다고 쓰지 않습니다.

```text
refactor(api): 응답 변환 로직 통합

- 호출부의 중복 변환을 공통 함수로 이동
- 기존 응답 형식 유지
```

- 제목은 `type(scope): 요약` 형식이며, `scope`는 패키지·영역을 구분할 때 붙입니다.
- 요약은 `추가`, `수정`, `제거`, `정리` 등 한글 개조식으로 작성하고 끝에 마침표를 붙이지 않습니다. 영문 고유명사·코드 식별자는 원래 표기를 유지합니다.
- 제목·본문·꼬리말은 줄마다 100자 이내로 작성하고, 본문·꼬리말 앞에는 빈 줄을 둡니다.

| 유형       | 용도                                    |
| ---------- | --------------------------------------- |
| `feat`     | 기능 추가                               |
| `fix`      | 오류 수정                               |
| `docs`     | 문서 변경                               |
| `style`    | 동작에 영향을 주지 않는 서식 변경       |
| `refactor` | 기능 추가·오류 수정 없이 코드 구조 변경 |
| `perf`     | 성능 개선                               |
| `test`     | 테스트 추가·수정                        |
| `build`    | 빌드·의존성 변경                        |
| `ci`       | CI 설정 변경                            |
| `chore`    | 기타 개발 환경·관리 작업                |
| `revert`   | 기존 커밋 되돌리기                      |

### 호환성 변경

호환성이 깨지는 변경은 `!` 또는 `BREAKING CHANGE:` 꼬리말로 표시하고 변경 내용과 전환 방법을 설명합니다.

```text
feat(api)!: 목록 응답 형식 변경

BREAKING CHANGE: 배열 응답을 items 필드가 있는 객체로 변경
호출부에서 응답 배열 대신 response.items 참조 필요
```

## 커밋 단위

기본 단위는 한 목적의 변경이며 독립적으로 검토·되돌릴 수 있게 나눕니다. 그 목적에 필요한 계약·호출부·테스트·문서는 함께 담습니다.
사용자가 지정한 범위·단위를 우선합니다. “스테이징한 변경”은 현재 인덱스에 있는 변경만 커밋하며, 분리하더라도 그 밖의 작업 트리 변경을 추가하지 않습니다.
같은 파일에 다른 목적의 변경이 섞이면 조각 단위로 나눕니다. 서로 의존해 분리하면 계약이 깨지는 변경은 한 커밋으로 유지합니다.

## 커밋 생성·재작성

저장소의 훅 설정과 연결 명령에서 검사·자동 수정·스테이징 반영·부분 스테이징 처리 방식을 확인합니다. 확인하지 않은 보존 동작을 가정하지 않습니다.

1. 요청 대상의 작업 트리·인덱스·커밋 diff를 읽고 커밋별 목적·내용·파일·조각·의존 순서를 정해 실행 전에 알립니다. 제공된 요청과 diff로 범위를 특정할 수 없을 때만 포함 여부를 질문합니다.
2. 원본 변경으로 잠금 파일·생성물이 달라져야 하면 해당 도구로 재생성해 같은 목적의 커밋에 포함합니다. “스테이징한 변경만” 요청에서 필요한 생성물이 빠졌으면 임의로 추가하거나 누락된 상태로 커밋하지 않습니다. 필요한 이유·파일을 알리고 포함 범위를 확인합니다.
3. 기존 인덱스와 작업 트리의 차이·부분 스테이징을 보존합니다. 파일 전체를 추가해 제외된 조각까지 섞지 말고, 대상 조각만 스테이징합니다. 범위 밖의 기존 스테이징은 되돌리지 않고 별도 인덱스·격리 작업 디렉터리로 커밋 대상에서 분리합니다.
4. 최종 인덱스 diff가 요청 범위와 일치하는지 대조합니다. 비밀값·로컬 환경 파일이 포함돼 있으면 커밋을 멈추고 해당 항목을 알리며 사용자 파일을 삭제하거나 범위 밖 스테이징을 임의로 해제하지 않습니다.
5. 커밋에 담길 상태에서 변경에 필요한 검사를 실행합니다. 작업 트리의 미스테이징 변경이 결과에 영향을 주면 격리된 작업 디렉터리 등에서 인덱스 상태를 검사합니다. 다른 상태에서 통과한 결과를 이번 커밋의 결과로 쓰지 않습니다.
6. Git 훅을 활성화한 상태로 커밋하며 우회하거나 실패한 상태로 자동 재시도하지 않습니다. 실행 뒤 인덱스와 작업 트리에서 요청한 조각·부분 스테이징의 보존 여부를 대조합니다. 훅이 파일을 수정했으면 바뀐 커밋 대상 상태에서 영향받는 검사를 다시 실행하고, 훅이 스테이징한 수정을 파일 전체 추가로 덮지 않습니다. pre-commit 통과는 전체 검사 통과를 뜻하지 않습니다.

메시지만 재작성할 때는 기존 스테이징을 새 내용에 포함하지 않습니다.

## 푸시

현재 브랜치·원격·대상을 확인한 뒤 요청한 대상에만 푸시합니다.

## 결과 확인

- 메시지만 작성했다면 초안과 근거로 삼은 변경 범위를 보고합니다. 커밋·amend·푸시를 수행한 것처럼 쓰지 않습니다.
- 커밋 후 새 HEAD의 내용과 남은 스테이징·작업 트리를 확인하고 해시·메시지와 함께 보고합니다.
- 검증한 대상(작업 트리·인덱스·커밋)과 최종 커밋의 일치 여부를 밝히고, 미검증 범위와 기존 실패·새 실패를 구분합니다.
