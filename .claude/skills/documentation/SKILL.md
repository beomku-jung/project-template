# 문서 작성·정제

독자의 작업에 필요한 조건·행동·결과를 근거와 함께 배치합니다. 문서 작성 요청만으로 구현·계약을 바꾸지 않습니다.

## 작업 절차

### 1. 독자의 작업과 근거 정하기

독자와 설명할 작업은 요청·기존 문서에서 파악하고, 설명할 내용에 따라 아래 근거를 찾습니다. 도구·저장소에도 없는 필수 정보만 질문합니다. 답을 얻지 못한 계약은 미확인으로 표시합니다.

| 설명할 내용         | 대조할 근거                     |
| ------------------- | ------------------------------- |
| 사용법·지원 범위    | 공개 API·명령·설정·테스트       |
| API 주석·사용 예제  | 선언·구현·호출부·동작 테스트    |
| 설계·선택 이유      | 요구사항·논의·현재 구현         |
| 작업 지침·작성 규칙 | 적용할 작업·실제 절차·기존 관례 |

사실은 현재 근거로, 가정은 전제로, 제안은 미결정 선택으로 표시합니다. 테스트 하나의 성공을 모든 환경의 보장으로 넓히지 않습니다. API 보장과 프로젝트 관례도 구분합니다.
설계 제안에는 비교할 대안과 판단 기준을, 결정 기록에는 선택 이유와 재검토 조건을 남깁니다.
선언·구현·테스트가 충돌하면 차이와 근거 위치를 보고합니다. 문구를 맞추려고 기본값·지원 범위·실패 동작을 새로 정하거나 구현을 고치지 않습니다.

### 2. 필요한 위치에 정보 놓기

정보 배치를 바꾸는 요청이 아니면 기존 제목·절 순서를 유지합니다. 독립된 작업은 제목으로, 실행 순서는 번호 목록으로, 선택 기준은 표로 나눕니다. 짧은 안내에 목차·표를 억지로 추가하지 않습니다.
Markdown 구성은 [구조와 예제](references/document-structure.md)를, 문서 유형별 배치는 아래 해당 참고 문서를 따릅니다.
표준 적용·적합성 판단, 제품 사용 설명서 작성·검토, ASD-STE100 검토를 요청받으면 [출처와 적용 범위](references/document-structure.md#출처와-적용-범위)를 읽습니다.

| 작업                  | 정보 순서·위치                                   | 참고                                                |
| --------------------- | ------------------------------------------------ | --------------------------------------------------- |
| 프로젝트 시작 안내    | 소개 → 최초 실행 → 관련 안내                     | [루트 README](references/readme.md#루트)            |
| 패키지·기능 사용 안내 | 소개 → 사용법 → 개발·제약                        | [패키지 README](references/readme.md#패키지)        |
| API 주석·계약         | 소유 선언에 계약, 사용 안내에 조합 절차          | [API 계약과 주석 위치](references/api-contracts.md) |
| 절차·작성 기준        | 적용 조건 → 예제 → 결과·판단 기준                | [사용 안내 예제](#사용-안내-예제)                   |
| 설계 제안·결정 기록   | 문제·제약 → 제안·근거 → 대안·확인 방법·결정 상태 | [설계안 예제](#설계안-예제)                         |

명령 앞에 작업 디렉터리·필수 설정·입력 파일을, 뒤에 성공 결과와 알려진 실패의 대응을 둡니다. 실제 공개 경로·명령을 쓰고 세부 설정은 소유 파일로 연결합니다.
파일 변경·외부 요청·삭제 등 실행 효과는 실행 전에 밝힙니다. 비밀값 대신 값의 용도와 제공 방법을 씁니다.
예제는 실행 가능·타입 검사 전용·발췌·템플릿·제안·모의 응답 중 해당 상태와 생략한 구현을 표시합니다. 생략된 구현이 있어 실행할 수 없는 코드를 실행 예제로 소개하지 않습니다.

#### 사용 안내 예제

루트 `test`가 Vitest를 실행하고 `@project-template/example` 프로젝트가 등록된 경우의 안내 예제입니다.

````markdown
# 특정 패키지 테스트하기

워크스페이스 설치를 마친 뒤 저장소 루트에서 실행합니다.

```sh
pnpm test --project @project-template/example
```

테스트가 실행되고 명령이 종료 코드 0으로 끝나면 성공입니다.
`No projects were found`가 나오면 루트의 프로젝트 검색 경로와 패키지의 테스트 설정을 확인합니다.
````

#### 설계안 예제

미결정 계약의 제안 예제입니다.

```markdown
## 제안과 근거

파일 내보내기에 작업 ID를 반환하고 결과를 조회하는 방식을 제안합니다.
큰 파일의 처리 시간이 HTTP 요청 제한을 넘길 수 있다는 가정입니다.

## 대안과 확인

지원할 최대 파일 크기·동시 요청 수에서 동기 응답과 작업 ID 방식의 처리 시간을 비교합니다.
동기 응답이 응답 시간 목표를 충족하면 동기 응답을 선택합니다.
측정 전이므로 방식은 미결정입니다.
```

### 3. API 설명과 설명 정본 정하기

API 설명에는 **호출자의 선택을 바꾸지만 선언만으로 알 수 없는 계약**을 씁니다. 설명할 항목과 소유 선언·사용 안내의 배치는 [API 계약과 주석 위치](references/api-contracts.md)를 따릅니다. 언어별 문서 주석 문법은 해당 언어의 규칙을 따릅니다.

설명 정본은 한 곳에 두고 다른 곳에서는 링크나 적용 예로 연결합니다. 버전·설정 전체를 복제하지 말고 관리 파일로 연결하되, 실행에 필요한 기본값·제약은 해당 사용 단계에도 씁니다.
변경된 이름·명령뿐 아니라 동작·지원 범위·설정·규칙을 관련 설명과 예제에 반영합니다. 그 변경에 영향받는 준비 조건·기대 결과·제약·문제 해결·이전 안내도 함께 갱신합니다.

작업 기록까지 정리하는 요청이면 현재 동작·제약·선택 이유는 사용 안내·API 계약·설계에 반영합니다. 미완료 작업·외부 준비 조건은 계획에, 재현·인수 근거는 리비전·환경·미확인 범위와 함께 검증 기록에 둡니다.
중간 기록은 정본에 정보가 옮겨졌고 삭제가 허용된 경우에만 제거합니다.

### 4. 변경한 문서 확인하기

표현만 다듬는 작업을 제외하고, 사용 안내를 작성·변경할 때는 준비 → 실행·판단 → 결과·실패 대응 순서로 따라갑니다. 빠진 단계와 행동·판단에 영향 없는 일반론을 찾아 고칩니다.
작업 지침에는 적용 사례와 제외 사례를, 설계안에는 같은 제약에서 대안을 고를 판단 기준을 둡니다.
원문과 수정본의 계약·금지·승인·예외·수치 범위를 대조합니다. 제목·목록·강조·HTML 주석의 범위와 코드 울타리의 짝도 확인합니다.

외부 출처는 설명 가까이에 확인할 내용이 드러나는 이름으로 연결합니다. 여러 자료는 주제별로 묶고 접근 제한은 밝힙니다. [외부 링크 예제](references/document-structure.md#markdown-외부-링크)를 참고합니다.
Markdown을 코드 블록으로 보여줄 때는 바깥 울타리를 안쪽의 가장 긴 울타리보다 길게 씁니다(안쪽 백틱 3개 → 바깥 4개 이상). 내부 코드가 블록 밖으로 나오지 않는지 확인합니다.

- 문서 변경: 사용 가능한 도구로 바뀐 문서의 **표시·링크·철자**를 확인합니다.
- 실행 예제 변경: 관련 실행·타입 검사로 확인합니다.
- 타입 전용 예제 변경: 타입 검사로 확인합니다.
- 구조·계약 제안: 명시한 전제와 대조합니다.
- 외부 서비스·데이터를 바꾸는 실행: 허용된 격리 환경에서만 합니다.
- 표현만 수정: 제품 빌드·배포·전체 테스트를 추가하지 않습니다.

실제 독자의 이해·성공이나 확인하지 않은 구현·환경까지 검증했다고 쓰지 않습니다.
결과에는 바뀐 문서·보존한 핵심 조건, 확인에 쓴 도구·범위·방법·결과, 미실행 검사·예제와 이유, 미확인 계약을 구분해 보고합니다.
